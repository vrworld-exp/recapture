## 2. Shared Conventions (inherited by ALL tasks)

**Permission architecture**
- ONE `PermissionService` facade is the ONLY permission API the app calls; `permission_handler` and the native `MethodChannel`s are reachable only inside the facade's implementation.
- Unified logical keys `AppPermission { camera, motion, storage|photos }` — reconcile `activityRecognition`→`motion` and `storage` vs `photos` (decision #3/#4).
- ONE backend per (permission, platform) via the explicit routing table; never two for the same cell; a missing route fails loudly in dev.
- All backend results normalize to `PermissionUiStatus { granted, denied, permanentlyDenied, restricted, limited, unavailable }`; backend types never leak out.

**The OS is the authority**
- The OS (via `PermissionService.check`) is the SOLE authority on grant status. Hive persists FLOW state only (asked / skipped / gate-progress) — NEVER grant status as authority. On resume, re-check live; live status wins on conflict.
- `check()` MUST NOT prompt (critical on iOS, where a status check that issues a motion query would pop the dialog).
- The OS prompt is triggered ONLY by explicit user action; never auto-fired on load/resume.

**Permanently-denied / Settings**
- never-asked and permanently-denied are distinct (Android: `shouldShowRequestPermissionRationale` + a persisted requested-before flag). never-asked → "Grant"; permanently-denied/restricted → "Open Settings".
- "Open Settings" routes through ONE path (no `permission_handler` + native duplication); launching Settings returns on open and does NOT report the user's choice — the post-Settings status is observed by the single resume re-check.

**Lifecycle**
- ONE app-lifecycle observer (owned by Screen 4A) performs the resume re-check; the deep-link, Hive flow-state, and analytics transition logic plug into it — no second observer.

**Native correctness**
- Android storage/activity MUST branch by API level (WRITE ≤28; READ legacy ≤32; granular media 33+; `ACTIVITY_RECOGNITION` runtime on 29+). Do not request no-op permissions.
- iOS usage-description strings (`NSCameraUsageDescription`, `NSMotionUsageDescription`, and Photos' key if requested) MUST be present or the first request hard-crashes.
- iOS Core Motion has no request API; `request(motion)` = a benign CMMotion query (prompts), `check(motion)` = `authorizationStatus()` (no prompt).

**UI**
- Design tokens + l10n; no hardcoded colors/dimensions/strings. Accessible (semantics, dynamic type, tap targets, text-scale resilience). Status conveyed by icon + text + color — never color alone.
- Tip surface is platform-adaptive (Material bottom sheet / Cupertino popover) behind one `show` API; platform selected via `Theme.platform` (test-overridable), not `Platform.isIOS`.

**Analytics**
- Extend the canonical `track()` layer + `AnalyticsEvent` const; one Zod schema per event; `snake_case`; hashed ids only (optional pre-auth); fire-and-forget (never breaks the flow).
- Permission and pre-capture events emit on TRANSITIONS / user actions only — never on passive `check()` or on rebuilds/resumes without a state change.

**Testing**
- Hermetic: mock the `PermissionService` facade; force platform; no real OS/permissions/network/device for widget tests. Deterministic, isolated, order-independent, with sabotage checks proving non-vacuity. Never modify production code to pass.

## 4. Inline Specs for Gaps

**iOS Settings routing counterpart.** The Android "Don't ask again → Settings" task implements a native settings intent; iOS needs an equivalent so the facade's `openAppSettings` works on both platforms. On iOS this is typically `UIApplication.openSettingsURLString` (or `permission_handler`'s `openAppSettings()` if iOS is plugin-routed). The facade picks the backend per the routing table; ensure the iOS path exists and returns a launch boolean like the Android one. Same correctness rule: returns on launch, does not report the user's choice; resume re-check observes the change.

**Earlier numbered screens (1–3).** Screen 4 and 4A exist; if the pre-capture flow has earlier screens, they need their own prompts. Confirm the flow's screen list and where the checklist sits.

## 5. Build Sequence (dependency-ordered)

**M0 — Decisions & shared types**
- Resolve §0. Create the shared `AppPermission` / `PermissionUiStatus` / `PermissionCriticality` types in the agreed location. Finalize the routing table. Settle Motion necessity (Android) and storage scope. Settle analytics naming.

**M1 — Native foundations (produce statuses)**

**M2 — The facade**

**M3 — UI**

**M4 — Persistence**
- Hive permission FLOW state, plugged into 4A's resume re-check (OS-as-authority; never auto-request on resume).

**M5 — Analytics**
- Permission events + pre-capture events, extending the canonical layer, transition-only, fire-and-forget.

**M6 — QA & hardening**
- Camera-gate test, iOS motion-prompt test, Android don't-ask-again test (each after its feature lands), plus the native detection instrumentation/manual matrix. Reconcile the four analytics batches' naming against the canonical tracking plan in one pass.

**Exit → Capture phase** when the Definition of Done is met; the gate's Continue/Start hands off to the capture route (next phase).

## 6. What NOT To Do (phase-wide)

- Do NOT let any task re-decide a §2 convention locally (a second permission API, a different status vocabulary, request-supplied grant authority, color-only status, a second lifecycle observer).
- Do NOT serve any (permission, platform) pair with two backends; do NOT call `permission_handler`/channels outside the facade.
- Do NOT cache grant status in Hive as authority; do NOT skip the live check on resume; do NOT auto-fire prompts on load/resume.
- Do NOT let `check()` prompt (especially iOS Core Motion); do NOT look for a Core Motion request API (it doesn't exist).
- Do NOT request no-op Android permissions (WRITE on 29+, READ_EXTERNAL on 33+); do NOT request media beyond the confirmed need; do NOT ship missing iOS usage strings.
- Do NOT confuse never-asked with permanently-denied; do NOT offer in-app re-request for permanently-denied.
- Do NOT gate capture on Motion/Photos — only Camera is required.
- Do NOT emit analytics on passive checks/rebuilds; do NOT break the flow on analytics failure.
- Do NOT modify production code to make QA tests pass; do NOT build the capture experience (next phase).
