## Implementation Instructions

### Step 1: Manifest declarations with API gating
Declare permissions with correct `maxSdkVersion`/gating (exact set depends on `targetSdkVersion` — confirm):
```xml
<uses-permission android:name="android.permission.CAMERA" />

<!-- WRITE is only meaningful up to API 28; ignored under scoped storage on 29+ -->
<uses-permission android:name="android.permission.WRITE_EXTERNAL_STORAGE"
    android:maxSdkVersion="28" />
<!-- READ_EXTERNAL_STORAGE effective up to API 32; superseded by granular media on 33+ -->
<uses-permission android:name="android.permission.READ_EXTERNAL_STORAGE"
    android:maxSdkVersion="32" />
<!-- Granular media permissions for API 33+ (request what the app actually needs) -->
<uses-permission android:name="android.permission.READ_MEDIA_IMAGES" />
<uses-permission android:name="android.permission.READ_MEDIA_VIDEO" />

<!-- Runtime permission on API 29+ -->
<uses-permission android:name="android.permission.ACTIVITY_RECOGNITION" />
```
Only declare the media permissions the app genuinely uses. Confirm the storage need (read-only? read+write? images only?) before finalizing.

### Step 2: Define the MethodChannel contract
A single channel (e.g. `mayasabhaxr/permissions`) with methods:
- `check(permission)` → returns a status string WITHOUT prompting.
- `request(permission)` → triggers the OS dialog (where applicable) and resolves with a status string when the result callback fires.
- `openAppSettings()` may be out of scope here (handled by the deep-link task) — confirm; if included, it just launches app details settings.
`permission` is a logical key the native side maps to the right concrete permission(s) for the running API level: `"camera"`, `"storage"`, `"activityRecognition"`.

### Step 3: Map logical permission → concrete permission(s) per API level
This is the core correctness logic:
- **camera** → `CAMERA` (runtime since API 23). Straightforward.
- **storage**:
  - API ≤ 28: request `READ_EXTERNAL_STORAGE` (+ `WRITE_EXTERNAL_STORAGE` if the app writes).
  - API 29–32: scoped storage; `WRITE_EXTERNAL_STORAGE` is effectively a no-op — do NOT request it. Request `READ_EXTERNAL_STORAGE` only if the app needs broad read.
  - API 33+: do NOT request `READ_EXTERNAL_STORAGE` (no effect). Request the granular `READ_MEDIA_IMAGES`/`READ_MEDIA_VIDEO` the app actually uses. (API 34 adds `READ_MEDIA_VISUAL_USER_SELECTED` for partial access — handle if the app supports partial selection.)
  - Aggregate the concrete results into one normalized `storage` status for Dart.
- **activityRecognition**:
  - API ≥ 29: runtime request `ACTIVITY_RECOGNITION`.
  - API < 29: it is NOT a runtime permission — treat as granted (no dialog).

### Step 4: Async request bridge
`request` is asynchronous: `ActivityCompat.requestPermissions(...)` returns immediately; the result arrives in `onRequestPermissionsResult`. Therefore:
- Store the pending `MethodChannel.Result` keyed by the request code; do NOT complete it synchronously.
- In `onRequestPermissionsResult`, look up the pending result, compute the normalized status, and complete it exactly once.
- Use distinct request codes; handle multiple concrete permissions in one request (e.g. read media images + video) and aggregate their grant results.
- Guard against a second `request` for the same permission while one is in flight.

### Step 5: never-asked vs permanently-denied (the gotcha)
`shouldShowRequestPermissionRationale` returns false BOTH before the first request AND after "don't ask again." To distinguish:
- Persist a "has been requested" flag per permission (e.g. SharedPreferences) set when a request is made.
- After a denial: if not granted AND `shouldShowRequestPermissionRationale == false` AND the permission was previously requested → **permanentlyDenied**. If not previously requested → still **denied/not-determined** (the dialog can still be shown).
- `restricted` (e.g. device policy) → if detectable, map accordingly; otherwise treat unrequestable states as permanentlyDenied with the manual path.

### Step 6: Activity + lifecycle safety
- `requestPermissions` requires a non-null Activity. If the channel is invoked with no attached Activity (backgrounded), return an error/normalized status rather than crashing.
- Handle configuration change / Activity recreation during a pending request: if the pending `Result` is lost (Activity destroyed), do not crash; the Dart side will re-check on resume (consistent with 4A). Avoid leaking the pending result.
- Use an `ActivityAware` plugin or properly forward `onRequestPermissionsResult` from `MainActivity` to the handler.

### Step 7: Normalize status for Dart
Return a stable string per permission that Dart maps to `PermissionUiStatus`:
`"granted" | "denied" | "permanentlyDenied" | "restricted"` (+ optionally `"limited"` if partial media selection on API 34+ is supported). Keep these strings identical to what the Dart mapping expects.

## MethodChannel Contract

```
Channel: "mayasabhaxr/permissions"

check(permission: "camera"|"storage"|"activityRecognition") -> String status   // no prompt
request(permission: "camera"|"storage"|"activityRecognition") -> String status // prompts; resolves on callback

status ∈ { "granted", "denied", "permanentlyDenied", "restricted" (, "limited") }

Native responsibilities:
  - map logical permission -> concrete permission(s) for the running API level
  - async-complete request() in onRequestPermissionsResult
  - track requested-before to detect permanentlyDenied
  - require Activity; survive config changes without crashing
```

## Task Description

Persist the app-side **permission flow state** in Hive so the app does not re-trigger OS permission prompts on resume/relaunch and doesn't re-show or nag the permission gate unnecessarily — while ALWAYS treating the operating system as the source of truth for actual grant status.

The critical correctness point (the naive implementation is dangerous): **Hive MUST NOT cache whether a permission is granted as the authority.** The OS is the only authority on grant/deny — the user can change permissions in Settings at any time. Hive persists only flow state (has-been-asked, user-skipped, gate-progress). On resume the app re-CHECKS live OS status (non-prompting) and the live status always wins over any cached assumption.

"Don't re-ask on resume" = on resume, re-check status without prompting; do NOT auto-fire the OS request dialog. The OS prompt is only triggered by explicit user action.

- [ ] Persist permission FLOW state in Hive: `hasBeenAsked`, `userSkipped` (for recommended/optional), and gate-progress — NOT the grant status as authority
- [ ] On resume/relaunch, re-check LIVE OS status via the permission facade (`check`, non-prompting); never auto-`request`
- [ ] Reconcile any conflict in favor of the live OS status (e.g. user revoked in Settings → flow state updates, gate re-shows)
- [ ] Use the flow state to avoid re-prompting and to skip/nag appropriately, not to assume permissions are granted
- [ ] Make the store durable (Hive, consistent with the persistence conventions) and resilient to missing/corrupt data (default to "not asked")

## Implementation Instructions

### Step 1: Define the persisted flow-state model
A small Hive-stored record per permission capturing ONLY app-flow facts (never the authoritative grant status):
```dart
class PermissionFlowState {
  final bool hasBeenAsked;     // app has shown the OS prompt at least once
  final bool userSkipped;      // user explicitly skipped a recommended/optional permission
  // optional gate-progress at the flow level (not per-permission):
  // bool gateCompleted;       // user passed the gate (Camera granted) — still re-validated live
}
```
Store keyed by the unified `AppPermission` (camera/motion/storage). Do NOT store a `granted` boolean as the source of truth.

### Step 2: Read flow state + live status together
When the gate/flow needs to make a decision, combine:
- LIVE status from `PermissionService.check(permission)` (non-prompting) — the authority on granted/denied.
- Flow state from Hive — whether we've asked, whether the user skipped.
Decisions:
- Never asked + not granted → it's fine to prompt on user action (first run).
- Asked before + not granted → do NOT auto-prompt on resume; show the current (denied/needs-settings) state and let the user act.
- User skipped an optional/recommended permission → do not nag every resume; respect the skip while still allowing manual enable.
- Granted (live) → proceed, regardless of what Hive said.

### Step 3: Resume behavior (no auto re-ask)
Integrate with Screen 4A's existing resume re-check: on resume, call `check()` for the relevant permissions (non-prompting) and update the UI/gate from the LIVE result. Under no circumstance call `request()` automatically on resume. Persisted flow state is read to avoid re-prompting and to decide nag/skip — it is not used to skip the live check.

### Step 4: Conflict resolution (live wins)
If Hive flow state implies one thing but the live OS status says another, the LIVE status wins and the flow state is updated:
- Hive says "asked + was granted in a prior session," live check says denied (user revoked in Settings) → treat as denied, re-show the gate / Settings path, keep `hasBeenAsked=true`.
- Hive says "skipped," live check says granted (user enabled in Settings) → treat as granted.
Never let stale Hive data mask a revoked permission.

### Step 5: Persistence durability + safety
- Use the app's Hive setup (adapters registered, same conventions as the project-persistence task). Flow state survives restart.
- Missing/corrupt flow state → default to a SAFE baseline: `hasBeenAsked=false`, `userSkipped=false` (i.e. behave as first-run for the flow). Never default to "granted/asked" in a way that skips a needed live check.
- Writes happen at the right moments: set `hasBeenAsked` when a request is actually triggered; set `userSkipped` when the user explicitly skips.

### Step 6: Expose to the UI
Provide the combined decision (live status + flow state) to the gate/cards via the app's state solution so the UI can: prompt on first ask, show denied/needs-settings without re-prompting, and respect skips — all reflecting live status.

## Component Contract

```
PermissionFlowStore (Hive-backed)
  get(AppPermission) -> PermissionFlowState   // hasBeenAsked, userSkipped
  markAsked(AppPermission)
  markSkipped(AppPermission)
  // NO grant-status authority stored here

Decision (combining live + flow):
  liveStatus = PermissionService.check(permission)   // authority
  flow       = PermissionFlowStore.get(permission)
  -> drives: prompt-allowed? auto-prompt? show-settings? nag? proceed?
Resume: re-check LIVE (non-prompting); never auto-request; live status wins over flow state.
```

## What NOT to Do

- Do NOT store/trust a "granted" flag in Hive as the source of truth — the OS is the authority; always `check()` live.
- Do NOT skip the live OS check on resume because Hive says it was granted before — the user may have revoked it.
- Do NOT auto-trigger the OS request dialog on resume/relaunch — re-check non-promptingly; prompt only on explicit user action.
- Do NOT add a second app-lifecycle observer — integrate with 4A's resume re-check.
- Do NOT let stale flow state mask a revoked permission — live status wins on conflict.
- Do NOT default missing/corrupt flow state to "granted/asked" — default to safe first-run flow.
- Do NOT duplicate the native "requested-before" tracking as a competing authority — coordinate layers (see Reconciliation).
- Do NOT call permission backends directly — go through `PermissionService`.

## Edge Cases to Handle

- [ ] Fresh install (no Hive flow state) → first-run flow; prompts allowed on user action.
- [ ] Granted last session, revoked in Settings between sessions → live check shows denied; gate re-shows; not auto-re-prompted.
- [ ] Skipped optional permission → not nagged on resume; can still enable manually; live status respected if later granted.
- [ ] Asked + denied previously → on resume, shown as denied (or needs-settings) WITHOUT auto-prompting again.
- [ ] Hive store missing/corrupt → safe first-run defaults; never assume granted.
- [ ] App killed mid-flow → flow state (asked/skipped) persisted; resumes correctly with live re-check.
- [ ] Permission granted in Settings while app backgrounded → resume live check upgrades it; flow proceeds.

## Constraints

- The OS (via `PermissionService.check`) MUST be the sole authority on grant status; Hive MUST NOT cache it as authority.
- On resume, the app MUST re-check live status and MUST NOT auto-`request`.
- On any conflict, live OS status MUST win and flow state MUST be reconciled to it.
- Hive MUST persist only flow facts (asked/skipped/gate-progress), durably, with safe defaults on missing/corrupt data.
- Integrate with 4A's single lifecycle observer; no second observer.
- All status access MUST go through `PermissionService`; backends not called directly.
- Coordinate with the native requested-before tracking so the same fact isn't double-sourced as authority.

- **Facade dependency:** Assumes the `PermissionService` facade exists and exposes non-prompting `check()`. This task uses it; it does not call `permission_handler`/channels directly.
- **Resume re-check ownership:** Assumes Screen 4A owns the single app-lifecycle resume re-check; this task plugs flow-state logic into it rather than adding another observer.
- **Native requested-before overlap:** The Android native task tracks "requested-before" in SharedPreferences for permanently-denied DETECTION (a native concern). This Hive flow state is a Dart/UX concern (asked/skipped/gate-progress). They are different layers; coordinate so neither is treated as the authority on grant status and the same decision isn't sourced twice. If desired, the Dart `hasBeenAsked` can be the single Dart-side flow flag while the native flag stays internal to detection.
- **Hive conventions:** Assumes the P0/persistence-test Hive setup (adapters, temp-dir testing). Reuse them.
- **Skip semantics:** Assumes recommended/optional permissions can be skipped and remembered; required (Camera) is never "skipped" (it gates progress). Confirm whether a skipped permission should ever be re-surfaced (e.g. once per N sessions) — default is respect the skip until manual action.

## 2. Shared Conventions (inherited by ALL tasks)

**Permission architecture**
- ONE `PermissionService` facade is the ONLY permission API the app calls; `permission_handler` and the native `MethodChannel`s are reachable only inside the facade's implementation.
- Unified logical keys `AppPermission { camera, motion, storage|photos }` — reconcile `activityRecognition`→`motion` and `storage` vs `photos` (decision #3/#4).
- ONE backend per (permission, platform) via the explicit routing table; never two for the same cell; a missing route fails loudly in dev.
- All backend results normalize to `PermissionUiStatus { granted, denied, permanentlyDenied, restricted, limited, unavailable }`; backend types never leak out.

**The OS is the authority**
- The OS (via `PermissionService.check`) is the SOLE authority on grant status. Hive persists FLOW state only (asked / skipped / gate-progress) — NEVER grant status as authority. On resume, re-check live; live status wins on conflict.
- `check()` MUST NOT prompt (critical on iOS, where a status check that issues a motion query would pop the dialog).
- The OS prompt is triggered ONLY by explicit user action; never auto-fired on load/resume.

**Permanently-denied / Settings**
- never-asked and permanently-denied are distinct (Android: `shouldShowRequestPermissionRationale` + a persisted requested-before flag). never-asked → "Grant"; permanently-denied/restricted → "Open Settings".
- "Open Settings" routes through ONE path (no `permission_handler` + native duplication); launching Settings returns on open and does NOT report the user's choice — the post-Settings status is observed by the single resume re-check.

**Lifecycle**
- ONE app-lifecycle observer (owned by Screen 4A) performs the resume re-check; the deep-link, Hive flow-state, and analytics transition logic plug into it — no second observer.

**Native correctness**
- Android storage/activity MUST branch by API level (WRITE ≤28; READ legacy ≤32; granular media 33+; `ACTIVITY_RECOGNITION` runtime on 29+). Do not request no-op permissions.
- iOS usage-description strings (`NSCameraUsageDescription`, `NSMotionUsageDescription`, and Photos' key if requested) MUST be present or the first request hard-crashes.
- iOS Core Motion has no request API; `request(motion)` = a benign CMMotion query (prompts), `check(motion)` = `authorizationStatus()` (no prompt).

**UI**
- Design tokens + l10n; no hardcoded colors/dimensions/strings. Accessible (semantics, dynamic type, tap targets, text-scale resilience). Status conveyed by icon + text + color — never color alone.
- Tip surface is platform-adaptive (Material bottom sheet / Cupertino popover) behind one `show` API; platform selected via `Theme.platform` (test-overridable), not `Platform.isIOS`.

**Analytics**
- Extend the canonical `track()` layer + `AnalyticsEvent` const; one Zod schema per event; `snake_case`; hashed ids only (optional pre-auth); fire-and-forget (never breaks the flow).
- Permission and pre-capture events emit on TRANSITIONS / user actions only — never on passive `check()` or on rebuilds/resumes without a state change.

**Testing**
- Hermetic: mock the `PermissionService` facade; force platform; no real OS/permissions/network/device for widget tests. Deterministic, isolated, order-independent, with sabotage checks proving non-vacuity. Never modify production code to pass.
- Real `shouldShowRequestPermissionRationale` / Core Motion behavior needs an emulator/device instrumentation step (or a documented manual matrix) — widget tests alone can't exercise it.
