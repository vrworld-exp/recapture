## Task Description

Implement a **hard gate on upload**: the control that initiates upload is **disabled whenever any level has fewer accepted shots than that level's absolute minimum**. This is a non-negotiable floor that protects the upload/reconstruction pipeline from receiving unusable data. The gate must be enforced two ways:

1. **Visually** — the upload control is disabled, with a clear, actionable explanation of which levels are short and by how much, plus a path to fix it.
2. **At the action** — the upload-initiation handler re-checks eligibility and refuses to proceed even if invoked, so the gate cannot be bypassed by a stale UI state. (A hard gate must enforce, not merely indicate.)

Relationship to the completion gate (earlier task): that gate is a soft "level complete → unlock Summary" check. **This** gate is a separate, hard floor — the **absolute minimum accepted shots per level** required to upload at all. It may use a lower, distinct threshold and must be evaluated independently of the soft completion rule (see Assumptions).

- [ ] Read each level's accepted-shot count and compare against that level's absolute-minimum config.
- [ ] Disable the upload-initiating control when any level is below its minimum.

```typescript
const PART_SIZE_BYTES = 5 * 1024 * 1024; // 5MB — S3 minimum for non-final parts
const PRESIGN_EXPIRES_SECONDS = 3600;     // 1 hour

export async function initiateMultipartUpload(s3Key: string, mimeType: string): Promise<string> {
  const result = await s3Client.send(
    new CreateMultipartUploadCommand({
      Bucket: process.env.S3_BUCKET_NAME,
      Key: s3Key,
      ContentType: mimeType,
    })
  );
  if (!result.UploadId) throw new Error(`No UploadId returned for key: ${s3Key}`);
  return result.UploadId;
}

export async function generatePartPresignedUrls(
  s3Key: string,
  uploadId: string,
  sizeBytes: number
): Promise<Array<{ partNumber: number; url: string }>> {
  const totalParts = Math.ceil(sizeBytes / PART_SIZE_BYTES);
  const urls = await Promise.all(
    Array.from({ length: totalParts }, (_, i) => i + 1).map(async (partNumber) => {
      const command = new UploadPartCommand({
        Bucket: process.env.S3_BUCKET_NAME,
        Key: s3Key,
        UploadId: uploadId,
        PartNumber: partNumber,
      });
      const url = await getSignedUrl(s3Client, command, {
        expiresIn: PRESIGN_EXPIRES_SECONDS,
      });
      return { partNumber, url };
    })
  );
  return urls;
}
```

pattern, unless the codebase is confirmed to be on AWS SDK v2 (check `package.json`

### Step 2: Create `src/services/manifestValidationService.ts`

```typescript
import {
  CaptureManifest,
  ManifestValidationError,
  ManifestValidationResult,
} from "../types/manifest";

export function validateCaptureManifest(
  manifest: CaptureManifest
): ManifestValidationResult {
  const errors: ManifestValidationError[] = [];

  // Rule 1: File count match
  if (manifest.files.length !== manifest.declaredFileCount) {
    errors.push({
      rule: "FILE_COUNT_MISMATCH",
      message: `Manifest declared ${manifest.declaredFileCount} files but contains ${manifest.files.length}`,
      detail: {
        declared: manifest.declaredFileCount,
        actual: manifest.files.length,
      },
    });
  }

  // Rule 2: Required levels present
  const presentLevelIds = new Set(manifest.files.map((f) => f.levelId));
  const missingLevels = manifest.requiredLevels.filter(
    (id) => !presentLevelIds.has(id)
  );
  if (missingLevels.length > 0) {
    errors.push({
      rule: "MISSING_REQUIRED_LEVELS",
      message: `Required levels missing from manifest: ${missingLevels.join(", ")}`,
      detail: { missingLevels },
    });
  }

  // Rule 3: Minimum photos per level
  const photosByLevel = new Map<string, number>();
  for (const file of manifest.files) {
    if (file.fileType === "photo") {
      photosByLevel.set(file.levelId, (photosByLevel.get(file.levelId) ?? 0) + 1);
    }
  }

  const underMinLevels: Array<{ levelId: string; count: number; required: number }> = [];
  for (const levelId of presentLevelIds) {
    const count = photosByLevel.get(levelId) ?? 0;
    if (count < manifest.minPhotosPerLevel) {
      underMinLevels.push({ levelId, count, required: manifest.minPhotosPerLevel });
    }
  }
  if (underMinLevels.length > 0) {
    errors.push({
      rule: "INSUFFICIENT_PHOTOS_PER_LEVEL",
      message: `${underMinLevels.length} level(s) have fewer than ${manifest.minPhotosPerLevel} photo(s)`,
      detail: { levels: underMinLevels },
    });
  }

  return { valid: errors.length === 0, errors };
}
```

This task adds tests only. It must NOT change the upload engine. If pause/resume re-uploads completed
parts or restarts, the test should FAIL and surface it — do not "fix" the engine here.

- [ ] Assert that after pause→resume, parts completed before pause are NOT uploaded again
- [ ] Assert that the upload resumes (does not restart from part 1 / byte 0)
- [ ] Assert the upload completes successfully with each part uploaded exactly once
- [ ] Assert progress (`bytesUploaded`) is monotonic across the pause/resume boundary (no reset, no double-count)
- [ ] Assert resume continues the same upload attempt (same `upload_id` / job), not a new one

## Files to Inspect First

1. The chunked upload manager (upload engine) — find `pause()`, `resume()`, the per-part upload path,
   how completed parts/ETags are tracked, and how the progress contract reports bytes/files. The tests
   drive these and assert against the tracked completed-parts state.
2. Existing upload-engine tests under `test/` — match the test style, the mock Dio / mock backend setup,
   and any fixtures for a session manifest (file list + sizes). Reuse them; do not build a parallel harness.
3. The HTTP seam — confirm Dio (or the backend client) is injectable/mockable so part PUTs can be counted
   and intercepted per part. If it is not injectable, the test cannot assert "no re-upload" cleanly (see
   Assumptions).
4. The progress contract — confirm `bytesUploaded` / `filesUploaded` / status are observable so the test
   can assert monotonicity and the paused→uploading transition.

## Implementation Instructions

### Step 1: Build a controllable upload scenario
Construct a test session with enough files/parts that a pause can land mid-upload with some parts
completed and at least one not yet started (e.g., a multi-part file). Use a mock Dio/backend that:
- records every part PUT (which file, which part_number, how many times),
- lets the test deterministically hold/delay a part so pause occurs at a known point.
Determinism is essential — no reliance on real timing or network.

### Step 2: Pause at a known mid-point and capture state
Drive the upload until a known set of parts has completed, then call `pause()`. Capture the set of
parts recorded as uploaded at pause time and the `bytesUploaded` value. Assert the status transitions
to paused and that no further part PUTs occur while paused.

### Step 3: Resume and assert no re-upload of completed parts
Call `resume()` and let the upload run to completion. Assert:
- No part PUT recorded before pause is issued again after resume (the core "same chunk / no re-upload"
  guarantee) — verify by per-part PUT counts: every part is PUT exactly once across the whole run.
- The first work done after resume is the part that was in-progress/next at pause, not part 1.
- The upload reaches completed status with all parts present.

### Step 4: Assert progress monotonicity and same-attempt continuity
Assert `bytesUploaded` never decreases across the pause/resume boundary and equals the full total at
completion (no double-count from a re-sent part). Assert the multipart `upload_id` (and ETag set) is the
same attempt across resume — resume did not abort+reinitiate a new multipart upload.

### Step 5: Cover the in-progress-part boundary explicitly
Add a case where pause happens while a part is mid-flight (not on a clean part boundary). Assert that on
resume that part is completed exactly once — depending on engine design it either finishes the in-flight
PUT or re-sends only that one incomplete part, but it must end up uploaded exactly once with correct bytes.
Document which behavior the engine guarantees and assert that one (see Assumptions).

## What NOT to Change

- Do NOT modify the upload engine, pause/resume logic, retry, or progress calculation — tests only.
- Do NOT change pause/resume signatures or add hooks to the engine purely to make testing easier; if a
  seam is genuinely missing, flag it rather than refactoring production code in this task.
- Do NOT delete or weaken existing upload-engine tests.
- Do NOT assert against wall-clock timing or real network behavior — keep the test deterministic.

## Edge Cases to Handle (as test cases)

- [ ] Pause on a clean part boundary (part N done, N+1 not started) → resume starts at N+1; parts 1..N
      never re-PUT.
- [ ] Pause while a part is mid-flight → that part ends up uploaded exactly once after resume.
- [ ] Multiple pause/resume cycles in one upload → no part ever PUT more than once; completes correctly.
- [ ] Pause→resume with zero parts completed yet (paused almost immediately) → resume proceeds from the
      start without duplicating the first part.
- [ ] Pause at the last part → resume completes that part and finalizes; no re-PUT of earlier parts.
- [ ] Resume called when not paused / double resume → no duplicate uploads, no crash (assert engine's
      documented behavior).

## Constraints

- Tests must be deterministic — controllable mock HTTP, no real sockets, no timing races.
- The core assertion is per-part PUT count == 1 for every part across the full pause/resume run; this is
  the unambiguous proof of "no re-upload."
- Assertions must distinguish "resumed same attempt" from "restarted new attempt" (compare upload_id /
  ETag continuity), since a restart can also end in success and would otherwise pass a naive test.
- `bytesUploaded` monotonicity across pause/resume must be asserted, not assumed.

## Acceptance Criteria

- [ ] Test pauses mid-upload with a known set of completed parts and asserts the paused state (no PUTs while paused)
- [ ] After resume, every part is uploaded exactly once across the whole run (per-part PUT count == 1)
- [ ] Resume continues from the in-progress/next part, not from part 1 / byte 0
- [ ] The upload completes successfully with all parts present and ETags collected once each
- [ ] `bytesUploaded` is monotonic across the pause/resume boundary and equals total at completion
- [ ] The resumed upload is the same multipart attempt (same upload_id), not a re-initiated one
- [ ] Mid-flight-pause case: the interrupted part ends up uploaded exactly once
- [ ] Multiple pause/resume cycles never cause any part to upload more than once
- [ ] All new tests pass against the current engine; `flutter test` green
- [ ] A deliberately broken engine (temporary local edit that re-uploads from start) makes the test FAIL —
      confirm manually, then revert
- [ ] No production code changed (tests/fixtures only); `git diff` limited to `test/`
- [ ] No analyzer errors (`flutter analyze` passes clean)

## Testing Instructions

1. Run `flutter test` on the new file; confirm all pause/resume cases pass against the current engine.
2. Inspect the mock's per-part PUT counts in each case and confirm each part == 1.
3. Temporarily modify the engine locally so resume restarts from part 1 (or clears completed-parts state);
   re-run and confirm the "exactly once" / "continues from same chunk" assertions FAIL. Revert.
4. Temporarily modify the engine so resume re-initiates a new multipart upload; confirm the upload_id-
   continuity assertion FAILS. Revert.
5. Run the mid-flight-pause case and confirm the interrupted part is uploaded exactly once.
6. Run `flutter analyze`; confirm zero issues and that `git diff` shows only test changes.

## Assumptions

- Assumed the upload engine exposes `pause()`/`resume()` and tracks completed parts/ETags per attempt, with
  an injectable HTTP layer so part PUTs can be counted. If the HTTP layer is not injectable or completed-part
  state isn't observable, a small testability seam is needed first — flag it and I'll scope that separately
  rather than write a test that can't actually observe re-uploads.
- Assumed "same chunk" means: completed parts are never re-PUT and resume continues at the part that was
  in-progress/next at pause. For a part interrupted mid-flight, the engine either finishes that PUT or re-sends
  only that single part — confirm which the engine guarantees; the test asserts the documented one, with the
  invariant being "each part uploaded exactly once."
- Assumed resume continues the same multipart `upload_id` rather than aborting and re-initiating; if the engine
  intentionally re-initiates on resume, the continuity assertion changes (but then "no re-upload" likely cannot
  hold, which would itself be the finding).
- Assumed a mock backend/S3 is available or trivially stubbable for part PUTs and completion; if tests must hit
  a real test bucket, the per-part PUT-count assertion needs request interception at the Dio layer instead.
- Assumed `bytesUploaded` is the engine's reported cumulative progress; the monotonicity assertion uses it.
