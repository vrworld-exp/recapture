16. NOTIFICATION TRIGGERS — what to send, and whether automatic or manual.
Principle: AUTOMATIC for anything the system already knows happened (one extra line in a code path
that already exists — worker terminal state, publish finalize, subscription sweep). MANUAL (admin
route / scripts/send-notification.ts) only for things a human decided: announcements, offers,
one-to-one account messages. One notification per event, targeted to the person it concerns, and
set expiresAt on anything time-bound so a user who signs up later does not inherit stale reminders.

  A. AUTOMATIC — system generated (priority order)

    A1. Subscription / payment (kind PAYMENT_DUE / PAYMENT_ACTIVATE) — same events as the SMS/WhatsApp
        reminder schedule in RECAPTURE_SUBSCRIPTION_PLAN.md §6, so build them together:
        : Trial started on first publish        -> "Your menu is live on a 30-day trial"        [Pay / view plan]
        : 7 days before, 1 day before, on expiry -> "Renew before <date> to keep your menu live" [Pay now]
        : Grace started + midway                 -> "Payment overdue — menu pauses in N days"    [Pay now]
        : Paused                                 -> "Your menu is paused. Pay to restore."       [Pay now]
        : Payment received / activated           -> "Payment received — active until <date>"    [View subscription]
        : Comped by admin                        -> "Complimentary until <date>"
        : Near slot cap at publish               -> "You're using 11 of 12 AR slots"             [Upgrade]
        Also send the rep a copy of trial/grace/paused for restaurants THEY activated (audience USERS).

    A2. 3D model lifecycle (kind INFO / SYSTEM) — a generation runs for minutes after the user leaves,
        today they only find out by re-pulling the Projects list:
        : Model ready (Meshy succeeded / optimized / staff submitted .glb) -> "Your 3D model for <project> is ready" [/projects or viewer]
        : Model generation FAILED (terminal)                               -> "We couldn't build a model for <project>" [retry / Preview]
        : Capture processing finished / failed (FILE_COUNT_MISMATCH, MANIFEST_INVALID) -> tell owner the next step

    A3. Catalog publish (kind INFO):
        : Publish PARTIAL or FAILED  -> "3 dishes didn't publish" [/catalog/publish]
          (SUCCEEDED needs none — user pressed the button and watched it; only notify if they left mid-run)
        : Rep published a restaurant -> notify the OWNER: "Your menu is live at <link>" — this is the owner's
          first touch when the rep created their account and they never opened the app.

    A4. Staff / rep events (targeted):
        : Standees assigned to a rep         -> "You've been handed 20 standees from batch <label>" [/rep/standees]
        : Restaurant delegated / activated   -> [/rep/catalogs/:id]
        : Role granted by script             -> "You now have MODEL_ARTIST access" (nice-to-have)

    A5. Analytics digests (kind ANALYTICS) — periodic, from the worker:
        : Weekly  -> "<restaurant> — 412 scans this week, top dish: Paneer Tikka" [/catalog/analytics]
        : Monthly summary.
        Only for published catalogs; SKIP when scans = 0 (a "0 scans" notification is demotivating).

  B. MANUAL — admin authored (what exists today via POST /admin/notifications / the CLI script)
    : Product announcements / new features ("AR Quick Look now works on iOS")
    : Offers and promos (yearly-plan discount) — always with expiresAt
    : Scheduled maintenance / outages (kind SYSTEM), expiresAt = end of window
    : One-to-one account messages (audience USERS): comp granted, refund processed, phone number fixed,
      manual payment recorded
    : Onboarding nudges for reps (targets, new batch printed)

  C. BUILD ORDER
    C1. A tiny notifyUser(userId, {...}) helper in notificationsService that every automatic path calls —
        one function, same schema as the admin route. Do this BEFORE adding any trigger.
    C2. Model ready / model failed triggers (highest daily impact, smallest change — the worker already
        has the terminal state).
    C3. Publish PARTIAL/FAILED + rep-published -> owner.
    C4. Subscription reminders — alongside stage 4 of the subscription plan (same schedule / ReminderLog).
    C5. Weekly analytics digest via the worker.

  D. CONSTRAINTS
    : Text stays PII-free on the analytics side (already handled — only kind/scope/hashed ids are tracked).
    : Every automatic send gets a dedupe key (e.g. key: 'model_ready:<modelId>') so a retried job never
      notifies twice — the unique partial index on Notification.key already gives this for free.
