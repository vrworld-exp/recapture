HOW A USER REACHES THE SUBSCRIPTION SCREEN AND SUBSCRIBES
=========================================================
(Plain-language walkthrough of the ReCapture owner flow, as built.)

THE FIRST-TIME OWNER'S JOURNEY
------------------------------

1. They capture dishes.
   The owner opens ReCapture, points the camera at a plate, walks around it,
   and the app uploads the photos. A few minutes later a 3D model of that dish
   is ready. They repeat for a few more dishes.

2. They build their menu (the "catalog").
   Each finished 3D dish is added to the menu as a product - name, price,
   category ("Starters", "Mains", ...). Plain photo-only items can be added too.
   All of this is a DRAFT; customers cannot see it yet.

3. They press Publish.
   The menu screen has a Publish button. Tapping it opens the Publish screen,
   which asks the server: "is this menu ready to go live?"
   (lib/presentation/screens/catalog/catalog_screen.dart -> _openPublish)

4. A checklist runs - and the subscription is checked twice, one way.
   Before anything goes live the server checks every reason the menu might not
   be ready - "a product has no name", "two dishes share a name", "no
   categories yet", and so on.

   The SUBSCRIPTION is checked by TWO things, against the same table:
     - the SERVER, as one more row on that checklist - but only once ops has
       flipped `subscriptionGatesEnabled` (see the caveat at the bottom).
       (recapture-api/src/services/subscription/subscriptionGate.ts)
     - the APP, on the Publish screen, always. It reads the subscription and
       runs the identical rules, so the question is asked the moment Publish is
       pressed whatever the server flag says. The server's answer wins wherever
       it gave one.
       (lib/domain/catalog/subscription_publish_gate.dart)

   The app's copy fails OPEN in every doubtful case: a subscription still
   loading, a failed read, or an API that sends no subscription DTO at all never
   blocks a publish.

   - First-time owner, no subscription at all
       -> row says: "No subscription yet - start a free trial or activate a
          plan to publish."  Publishing is BLOCKED.
   - Plan lapsed (PAUSED / CANCELLED) but the menu has only photo items
       -> still publishes. Only 3D dishes need a plan.
   - Plan lapsed and the menu has 1+ 3D dishes
       -> "Your 3D menu needs an active plan." BLOCKED.
   - Plan running but more 3D dishes than the plan covers
       -> "Menu has N 3D dishes; your <plan> covers M." BLOCKED.
   - GRACE (just lapsed, inside the grace window)
       -> never a blocker; a warning banner instead.

5. The block is a CARD, with the way out on it.
   A subscription blocker is not a checklist row. It is the first card on the
   Publish screen, and it carries the reason, the 3D-dish numbers behind it, the
   second way out ("archive your 3D dishes and publish a photo-only menu", which
   genuinely works), and one button: "See plans" where a tier still has to be
   chosen, "Pay now" where the plan is already known. The Publish button is off
   while it is up. The owner does not go hunting for any of it.
   (lib/presentation/widgets/catalog/publish_body.dart -> _SubscriptionPaywallCard
    lib/domain/catalog/subscription_copy.dart -> publishPaywallCopy)

6. On the Subscription screen they pick a plan and pay.
   The screen shows "No subscription yet", how many 3D dishes the menu has,
   and the three plans side by side (monthly / yearly).
   They tap a plan -> Pay -> the Razorpay sheet opens INSIDE the app
   (native SDK on Android/iOS, Checkout.js overlay in a browser) -> they pay
   by UPI / card.
   The app never trusts the SDK's "success" popup. It polls the server until
   the server says ACTIVE, then shows "Payment received - your plan is active."
   (lib/presentation/screens/catalog/subscription_screen.dart,
    lib/application/catalog/checkout_notifier.dart)

7. They go back - and the publish they asked for happens by itself.
   Returning to the Publish screen re-reads the subscription and then the
   checklist. The card disappears - and because the press that opened the screen
   is still ARMED, the run starts on its own: the menu goes live and the QR code
   works without a second Publish tap.
   (lib/presentation/screens/catalog/publish_screen.dart -> _maybeAutoStart,
    _openSubscription)


THE FREE-TRIAL SIDE DOOR
------------------------

The owner CANNOT start the free trial themselves - there is no owner route
for it. The 30-day trial (up to 10 3D dishes, one per restaurant) is started
by:
   - a SALES REP from the rep app  ("Start free trial" on the restaurant card,
     POST /rep/catalogs/:id/subscription/trial), or
   - an ADMIN                       (POST /admin/catalogs/:id/subscription/trial)

So for a rep-onboarded restaurant the trial is usually already running by the
time the owner presses Publish, and they never see the block at all. They meet
the Subscription screen ~30 days later, when the trial ends and the menu
screen shows "Your free trial has ended - choose a plan within N days to keep
3D live", with a button to the plans.

Second door: the menu screen header carries a small subscription chip
("No plan" / "Trial 12d" / "Active") that opens the same Subscription screen
at any time.

Third door (rep side): the rep can press "Notify owner to pay", which sends
the owner an SMS + in-app nudge pointing at the Subscription screen.


LIFECYCLE AFTER PAYING (short version)
--------------------------------------

   NONE ---(rep/admin trial)---> TRIAL ---(period ends)---> GRACE
   NONE ---(owner pays)--------> ACTIVE --(period ends)---> GRACE
   GRACE --(owner pays)--------> ACTIVE
   GRACE --(grace window ends)-> PAUSED   (3D switched off on the live menu;
                                           photo menu stays up)
   PAUSED -(owner pays)--------> ACTIVE   (3D switched back on)
   Catalog deleted ------------> CANCELLED (no refund, trial not reset)

Paying while ACTIVE / TRIAL / COMPED starts the new period at the payment
date - the remaining days are forfeited, and the checkout section warns about
this before the Razorpay sheet opens.


IMPORTANT CAVEAT - THE FLAG
---------------------------

The server-side flag `subscriptionGatesEnabled` is NOT flipped yet (it is the
last ops step in docs/subscription/rollout.md). Until it is, the SERVER adds no
subscription row, and `POST /catalog/publish` will publish a catalog that is on
no plan at all.

The APP asks anyway: the Publish screen runs the same rules client-side and
shows the paywall card, so the walkthrough above is what an owner sees today.
Two things worth knowing while the flag is off:

  - the app is the ONLY thing enforcing it. An older build of the app, or any
    other client, publishes without a plan.
  - the two can only disagree in the safe direction: the app may refuse a
    publish the server would have allowed. It never allows one the server
    refuses, because the server's gates win wherever it produced any.

Flipping the flag changes nothing about what the owner sees - the same card
renders from the server's gate instead of the client's evaluation - and makes
the refusal real.
